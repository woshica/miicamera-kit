# H.265 试录与容量对比

> 本文中的命令、配置和资源路径均相对于软件包根目录 `miicamera-kit/`；辅助入口在 `test/`，旧方案入口在 `test/legacy/`。

2026-10-25：按用户要求增加独立的 H.265 录制试验，参考已认可的官方样片使用长 GOP 和 B 帧，编码通过 FFmpeg/NVIDIA NVENC 完成。没有调用或复制 ImageView 的私有编码实现；CQ 数字与官方质量100不存在已知等价换算。

## 如何试录

1. 先正常停止 ImageView 录像、关闭相机预览，确认镜头朝向有细节的测试目标且光照可用。两个程序不能同时占用相机。
2. 双击包根目录下的 `test/legacy/试录H265一分钟.cmd`，阅读提示后按键开始。它运行60秒，用20秒名义视频时长分段检查衔接；末段可能不足20秒。
3. 当前使用 `config/mouse-4k45-hevc-trial.json`：3840×2160、45fps、`hevc_nvenc`、p5、CQ23、GOP250、B帧3、YUV420 8bit、曝光10ms、增益100%。新配置未包含固定成像覆盖；SDK打开设备后的白平衡等不能假定与 ImageView 内一致，最终值见 `profile-used.json` 的相机读回记录。
4. 默认视频保存在包外 `camera-recordings`，本仓库中则为 `private/source/data/camera-recordings/`。每次新建唯一目录，不覆盖既有数据。视频使用 MKV 容器及 H.265 编码，同时记录逐帧 CSV、`capture.json` 和 `profile-used.json`。MKV/MP4 是容器差别，不是之前容量差距的主要原因。
5. 等待解码帧数检查完成，再看 `capture.json` 的 `status`。错误或队列溢出会停止并标为不完整；不会用重复帧掩盖。短测通过仍需在真实小鼠日夜场景回看细节。

JSON 自身默认只录60秒，`segment_seconds: 3600` 保留每小时分段设置；一分钟入口临时覆盖为20秒，方便检查换段。分段由同一个连续编码进程完成，按收到的帧数和45fps名义播放时长切分，实际采集时间以 CSV 为准。它不保证恰在墙上时钟整点换文件，也不代表72小时稳定性已通过。

CQ 越小通常越偏向保留细节、文件越大；CQ20、23、26仅是本次试验档位。`rate_control: quality` 下 JSON 中的24/26Mbps字段不参与编码，不是码率上限。质量模式容量随场景变化；10GiB余量检查和950GB停止保护继续生效，950GB保护约每2秒检查且触发会中断，不能据此保证完整72小时低于1TB。

本试验明确要求可用的 NVIDIA HEVC 硬件编码；不可用时会报错，不会悄悄切换成 H.264。原有官方入口和旧 H.264 JSON 保持原用途。

## 同一内容的离线对比

输入为用户已认可的官方 MP4 样片，时长50.013秒、10.36MB、3840×2160、HEVC。它的文件头记2202帧，实际可解码2201帧；所有试验输出也可解码2201帧。输出 MKV 时长50.022秒，存在容器时间基准的舍入差异。

| 方案 | 文件大小（十进制MB） | 平均码率 | 相对已解码官方样片的SSIM |
|---|---:|---:|---:|
| 官方原文件 | 10.36 | 1.66Mbps | 参考文件 |
| 原 H.264 24/26Mbps、GOP45、B0 | 143.79 | 23.00Mbps | 0.997188 |
| H.265 CQ20、p5、GOP250、B3 | 46.88 | 7.50Mbps | 0.997817 |
| H.265 CQ23、p5、GOP250、B3 | 30.94 | 4.95Mbps | 0.997447 |
| H.265 CQ26、p5、GOP250、B3 | 21.89 | 3.50Mbps | 0.996956 |

大小与码率测量覆盖整段；SSIM只比较前450个解码帧，按帧序号对齐，避免 MP4/MKV 时间戳精度差异造成错配。SSIM描述额外压缩后与该参考的相似程度，不是画质百分比或小鼠行为可辨识度验收。

**这些是已压缩视频的再次编码结果，不能据此预测原始相机直录的码率。** 原文件已经损失或去掉的纹理、噪声不会因解码恢复。新 H.265 文件仍比官方原文件大，说明仅复现格式、GOP和B帧不等于完全复现其质量控制。此次缩小也同时涉及码率控制与其他参数，不能全部归因于H.265本身。

可用 `scripts/compare_hevc_sample.py` 对其他已完成视频重复比较；它要求新的或空的输出目录，保留原文件。开发机证据在环境包外 `private/qa/scratch/hevc-trial-20261025/offline/results.json`，包含命令、探测结果和 SSIM 日志，迁移软件包不附带这些私人视频。

## 验证范围

- 配置解析、旧 H.264 路径、HEVC B帧跨段帧顺序已经过针对性检查；分段首帧为关键帧，各段 CSV 和解码帧数吻合。
- 实时4K合成输入暴露出编码器启动瞬间队列溢出：8帧队列在约0.25秒填满。诊断中只扩大临时队列后，启动峰值约11–12帧，随后降至约1帧且没有持续增长。因此仅将 HEVC 队列改成16帧（4K RGB排队图像最多约398MB），旧H.264仍为8帧。90帧启动回归检查和450帧/5段合成输入检查通过；队列真正满时仍报错，不静默丢帧。
- 把整段官方样片解码为RGB送入实际 Writer 后，3段为900/900/401帧，与CSV和原片可解码2201帧对应，视频合计35.94MB。不过该回放输入实际只达到约25.03fps，因此这一步只验证真实画面编码与分段帧数，不作为45fps相机吞吐量证据。其视频按45fps名义播放，不能用播放时长冒充实际采集时长。
- 原始相机直录已通过上述60秒短测；实际小鼠画质、真实一小时边界和72小时连续运行仍需分别验收。不能用样片转码或合成画面测试替代这些项目。

编码路径依据：[NVIDIA 官方 FFmpeg/NVENC 使用说明](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.0/ffmpeg-with-nvidia-gpu/index.html)。实际可用参数以本包 FFmpeg 的 `-h encoder=hevc_nvenc` 为准。

## 2026-10-26：官方编码参数与体积差异的更正

官方样片的HEVC编码信息SEI包含x265的UUID和参数正文：`rc=crf crf=21.0 keyint=250 bframes=3 rc-lookahead=10 aq-strength=0.00`，并启用CU-tree。该样片指向x265软件编码；后来界面中的GPU选择不能反推历史文件的编码器。信息SEI依据见 [x265源码](https://mailman.videolan.org/pipermail/x265-devel/2014-July/004805.html)。这只确认该份文件留下的参数，不代表所有官方“质量100”都对应CRF21。

后续已直接定位回退原因：明确选NVIDIA RTX3070、质量100后，ImageView请求旧 `NV_ENC_PRESET_LOW_LATENCY_HP_GUID`，610.88驱动返回12／不支持的参数，硬件创建失败后libx265创建成功。NVIDIA从590驱动起移除此旧预设。新片48.582秒、100.10MB、1066个解码帧，平均约21.94fps；不能由预览45fps推定实际录制45fps，也不能从软件流的CRF21反推NVENC CQ。详细原因与官方更新需求见 [官方录像流程](official-recording-workflow.md)。

此前自制HEVC采用NVENC CQ23，未匹配官方编码器及质量控制。前10秒的片级基础QP中位数，官方30、自制CQ23为20；两者均有2201个可解码帧、9个关键帧、250帧间隔和接近的B帧比例，容器开销不足0.05MB，不能解释约20MB大小差距。片级基础QP不是每个块的最终QP，也不是视觉画质评分。

完整官方样片10.36MB；保持4K、HEVC、GOP250/B3，将NVENC质量改为CQ32后离线结果为11.35MB，平均约1.81Mbps。另按已提取参数使用当前x265 4.2软件编码前450帧，视频包约1.410MB，官方前450包约1.413MB，已非常接近。逐帧相似度SSIM分别为CQ32 0.995269、x265复现0.996593，参考仍是已压缩官方视频，不能当作相机原始画质的等价证明。

虚焦通常降低细节；偏暗是否增加容量取决于噪声等因素。此前偏暗、虚焦的直录画面仅限制容量外推和小鼠画质验收，**不是官方文件更小的解释**。本轮对照支持编码器和压缩参数不匹配才是需要修正的方向。

没有更改当前CQ23试录JSON或启动入口，也没有调用相机。x265短片复现不代表已完成相机实时接入及长录测试。开发机的完整命令、视频和日志在包外 `private/qa/scratch/imageview-encoder-study-20261025/`；这些私人样片不随软件包迁移。
