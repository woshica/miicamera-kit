核验日期：2026-10-28。下文保留早期私有仓库阶段的方案评估。

**同日后续状态：** v2026.10.28 完整交付包已发布，负责人随后明确要求将仓库改为公开。公开 Release 的浏览器下载不再需要登录或个人令牌；下文的私有身份方案仅作历史记录，不再是当前下载前提。在线一键更新仍未实现。现有「安装更新.cmd」只对已下载、解压的本地累计更新内容进行校验、备份和安装；当前完整 ZIP 仍需整包下载，不是联网按差异下载。现行步骤见[客户下载与安装指南](客户下载与安装指南.md)。

## 结论

可以实现客户双击「检查并更新.cmd」完成更新。推荐从 GitHub Release 下载经过验证的版本化小型更新 ZIP，再复用现有离线安装器；不建议把客户入口做成 `git pull`。首次需配置获授权的下载身份，之后才可能做到一次点击。没有 GitHub 下载权限或不能联网的现场，继续使用离线更新 ZIP。

- 当前最新正式 [Release v2026.10.26](https://github.com/woshica/miicamera-kit/releases/tag/v2026.10.26) 于 2026-10-26 08:20:27 UTC 发布，非草稿、非预发布。
- 该 Release 只有 `miicamera-kit-v2026.10.26.zip`（951,556,533 字节，约 908 MiB）及其 `.sha256`，尚无小型更新附件。
- [README](../README.md) 明确该完整包仍为旧 TOML/CMD 工作流；本地新版工作台及更新安装器不能视为已发布能力。
- [完整包脚本](../scripts/package-release.py) 明确不打包 `.git`、现场 `config/operator/` 和客户根目录 TOML；[忽略规则](../.gitignore) 排除 `runtime/`、`sdk/`、`installers/`。所以客户解压目录通常不是 Git 工作副本，源码 clone 也不能直接运行。
- [本地安装器](../scripts/install-update.py) 已支持逐文件 SHA-256、路径白名单、停止状态检查、客户配置初始化/保留、旧入口归档、变更文件备份，以及捕获安装异常后的回滚；[维护说明](维护人员配置说明.md) 要求更新后校验及一分钟试录。这些构成可复用的本地基础，并非完整在线更新系统。

## 为什么不直接 fetch / pull

`git fetch` 只取回 Git 对象，`git pull` 进一步将远端分支整合到当前分支，可能涉及快进、合并或变基及冲突；它不是安装事务。[Git 官方说明](https://git-scm.com/docs/git-pull)

即使预装 Git、初始化客户目录并处理认证，拉源码仍不会补齐被忽略的运行依赖，也不会自动执行旧 TOML 到工作台配置的迁移、旧入口归档和包清单验证。跟随 `main` 还会把尚未发布的开发状态送到现场。`--ff-only` 可以拒绝分叉，不能解决这些问题。不要使用 `reset --hard`、`clean` 或静默丢弃现场修改来实现“一键”。开发维护机可继续用 Git，客户交付以 Release 为单位。

## 建议的客户体验与实现边界

以下为待实现流程：

1. 双击更新入口，显示已安装版本和可用稳定版本。查询一次 Release 后固定 tag、附件 ID 和哈希，后续下载使用同一版本，避免更新途中“latest”变化。没有新版本直接退出；不得仅按字符串比较日期版本。
2. 在软件包外临时目录下载指定更新 ZIP、校验信息和更新元数据。核对仓库、附件名、大小、SHA-256、允许的来源版本/配置版本及运行依赖指纹；失败保持原安装可用。安全解压时拒绝越界、链接、重名和异常大小等内容。
3. 明确要求停止录制并等待收尾验证，退出预览、工作台后台和 ImageView；安装前再次检查并保持互斥，防止检查后重新启动。现有进程检查可以复用，但尚不能当作完整的并发锁。
4. 从独立更新目录运行安装器，保留客户 `config/operator/`、历史配置原文和匹配依赖。录像仍放包外；不扫描上传录像、诊断或客户参数。
5. 保留备份和恢复记录，安装后执行固定文件校验、配置加载及启动检查，记录版本/tag/摘要。现有异常回滚不涵盖断电、自检失败或成功安装后主动降级，需补充恢复入口及恢复流程；失败不得标记为更新成功。操作员完成一分钟试录、回看和参数快照核对后再正式使用。

建议 Release 同时提供完整包、代码更新包、各自 `.sha256` 和版本元数据；完整包用于首次安装或依赖升级，代码包仅用于兼容基线。当前安装器不更新运行依赖，不能把完整包直接作为小型更新包输入。依赖不匹配时应停止并指引维护人员迁移，不能用简单脚本覆盖。

首版可由维护人员安装 GitHub CLI、配置客户自己的获授权账号，下载后调用现有安装器；客户入口封装这些步骤。CLI 支持省略 tag 下载最新 Release，且可按附件模式筛选；正式安装仍应先解析并固定 tag。`--archive zip` 获取的是源码包，不是可运行的交付 ZIP。[gh release download](https://cli.github.com/manual/gh_release_download)

后续若不想现场安装 CLI，可用随包 Python 调用 Releases API。官方 API 提供最新正式 Release 与附件下载；下载需支持 200/302，重定向时不得把 Authorization 头泄露到无关主机。在线层仍需处理网络中断、代理、下载重试、磁盘空间和权限错误。[Releases API](https://docs.github.com/en/rest/releases/releases#get-the-latest-release)、[附件下载 API](https://docs.github.com/en/rest/releases/assets#get-a-release-asset)

## 私有访问与实施前决策

私有附件不能依赖匿名永久链接。上述 API 对私有资源要求有效身份；细粒度令牌需要对应仓库的 `Contents: read`，也支持 GitHub App 身份。浏览器已登录不等于脚本自动拥有下载身份。CLI 登录默认使用系统凭据存储，系统存储不可用时可能退回明文文件，现场部署必须确认实际存储方式。[附件认证要求](https://docs.github.com/en/rest/releases/assets#get-a-release-asset)、[gh auth login](https://cli.github.com/manual/gh_auth_login)

实施前需确定：

- **分发身份与源码可见范围：** 是否允许客户账号读取当前私有源码仓库；如只允许取交付包，应另行设计受限分发渠道。邀请成员、另建分发服务或改变可见性涉及访问范围，须先取得授权。本次没有执行这些动作。
- **凭据生命周期：** 客户自有身份或受控的短期凭据，最小权限、可撤销、到期后有明确重登提示。不得把开发者个人 PAT、App 私钥或共享长期密钥塞进 CMD、ZIP、日志、源码或 URL。采用 App 时，私钥留服务端，不交给客户端。
- **稳定发布与兼容口径：** 谁确认新版可供现场使用、最早可升级版本、运行依赖指纹、配置迁移和回退兼容范围；同名附件不原地替换。哈希可发现损坏，但若包和哈希同时遭替换，不能单独证明发布者身份；需按威胁模型决定签名清单。
- **运行条件与恢复：** 客户网络能否访问 GitHub、是否允许 CLI/登录、安装目录可写和备份空间是否充足，以及安装失败/断电后的恢复方式。离线包应保持为长期备用路径。

建议先确认身份和分发范围，再实现“Release 下载 + 现有安装器 + 版本/兼容元数据 + 自检恢复”。本报告不证明客户现场网络、相机或长录已经验证，也不意味着当前 Release 已具备新版更新能力。
