## 本轮设置

- 相机：E3ISPM08300KPD，SDK 60.32549.20260908，USB3连接；3840×2160、名义45 fps、速度档4。
- 编码：`hevc_nvenc`、`quality`、CQ30、p5、GOP250、最多3个连续B帧、8bit YUV420、MKV无音频。
- 相机：固定曝光12000微秒、增益1016%（约10.16倍）、白平衡5468/1163；沿用室内对照条件，不是正式小鼠成像的统一推荐值。
- 试录临时使用20秒分段；交付TOML默认录制1小时、每3600秒分段。分段按名义编码时间，相机实测帧率略高于45，所以会有一个很短的末段。
- 编码队列保持16帧，未增大缓冲、忽略帧号缺口或补入重复帧来获得通过结果。

## 两类异常的证据与边界

第一次异常是16帧编码队列溢出。发生在第一个分段附近，但现有实现使用同一个连续FFmpeg进程，换段不会重新启动编码器。下一次60秒监测的队列峰值为8帧，之后排空，没有观察到持续积压，尚不能据此定位第一次短暂阻塞的根因。第一次录制期间ImageView进程曾启动，但没有证据证明它抢占了相机或导致失败。

统一入口那次缺口发生在约34.4秒：SDK序号1554后直接出现1556，设备时间间隔约44.24ms，接近正常22.12ms的两倍，位置不在20秒分段切点。所有交给编码器的2710帧均在输出中解码得到，因此这次异常位于编码前的采集/SDK链路，不能归因于H.265压缩丢帧。仅凭这些日志仍无法区分设备、USB、驱动或SDK内部原因。软件丢帧计数与前后端满计数均为0，不等于源帧序号连续。

因此，短片已有完整通过实例，但当前不能宣称连续72小时可靠。现场应保持相机独占，保留 `capture.json`、`profile-used.json` 和逐帧CSV，逐步进行更长时长验证；出现 `incomplete` 时保留文件与日志，不作为完整记录验收。
